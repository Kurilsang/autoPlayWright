为什么要建 autoPlayWright？

被测对象是内部 Agent 产品的 Web 端与 Electron 客户端——先看清问题，再谈方案。
痛点 1双端产品，页面多、链路多
Web 端 + Electron 客户端，会话创建、对话、工具调用展示、文档处理、工作流……核心链路成体系地增长。
痛点 2核心链路零自动化
完全没有自动化覆盖，版本一到全靠手工回归。成本高、周期长，且不可持续。
痛点 3LLM 回复非确定
Agent 回复由 LLM 生成、措辞每次不同。传统「断言固定文本」的写法会大量假失败，用例写了也不敢信。
痛点 4逐条手写不现实
页面数量大、链路数量多，写用例的速度追不上页面改版的速度，人力线性堆不上去。
结论：靠人肉回归撑不住，需要一套 可复用、可判信、可持续维护 的链路自动化资产。

02

它解决什么？

一句话：把「逐条写代码」压缩成「写/审一个 YAML」，并且让结果可信、可追溯。
  • ▸
    新增用例 ≈ 写/审一个 YAML
    业务链路用 DSL 描述（导航→输入→发送→断言），不写 Python 代码
  • ▸
    一次编写，双端执行
    Web / Electron 共享同一套 Page Object，platforms 字段控制生效矩阵
  • ▸
    改版不怕：定位器仓库
    命名定位器多候选回退：testid > role+name > placeholder/label > text > css/xpath
  • ▸
    断言不抖：只测确定性内容
    组件 / 状态 / 结构；「完整回答六信号」判完才断言，不再因 LLM 措辞假失败
  • ▸
    失败即取证，禁止自愈
    归因分类 + 复现 + 信号时间线 + 冻结截图入报告，缺陷不被重试跑绿
  • ▸
    结果可消费
    步骤级 JSON（机器/看板）+ 单文件 HTML 报告（人）+ Allure 可选
  • ▸
    AI 半自动生成
    爬虫快照 → LLM 草稿 → 人工评审入库 → CI 稳定回放
flows/example_chat.yaml 
meta: { id: example-chat, platforms: [web], tags: [P0] }
steps:
  - do: { page: agent_chat, action: send_message,
        args: { text: "你好，夹具" } }
  - do: { page: agent_chat, action: wait_reply_done }
  - do: { page: agent_chat, action: capture_context }
  - assert: { type: visible, target: message_list }
  - assert: { type: text_contains,
        target: message_list, expected: "你好，夹具" }
  - judge: { note: "v1 预留" }
闭环生产闭环
写 YAML → schema 校验 → pytest 解释执行 → JSON/HTML 报告 → 失败取证回流修复。
JSON 第一公民 report.html 零依赖 Allure 可选

它明确不解决什么

边界先说清楚——这些都写进了 SPEC 的 Out of Scope，不承诺、不兜底。
  • ✕
    LLM-as-Judge 的判定实现
    只预留 schema 字段与接口形状，判定逻辑后置接入
  • ✕
    全自动探索式测试
    AI 不自主漫游页面；生成物必须人工评审后才入库（D2/D10）
  • ✕
    后端接口测试 / 造数、性能压测
    只测 UI 的外部行为，接口与性能各有专门手段
  • ✕
    视觉像素级回归、移动端
    覆盖目标是 Web + Electron 两端，不做像素比对
  • ✕
    mock LLM 后端
    Agent 产品必须测真实链路，mock 出来的绿灯没有意义
  • ✕
    测试平台 / 看板本体
    框架只负责输出标准 JSON，消费端交给内部平台
  • ✕
    手工用例 ↔ 自动化用例的管理映射系统
    不做用例管理平台，用例即仓库里的 YAML 文件
定位：链路回归资产，不是测试体系的全部。 只做「确定性、可复用、可判信」的那一层，其余交给对应领域的专门工具。

为什么不做全量覆盖？

不是能力问题，是性价比问题：全量在高频改版 + LLM 限流的现实里跑不动、也守不住。
成本UI 高频改版
页面一改，全量用例成片变红，维护成本超过回归收益。D11 的判断：靠数量堆不出稳定。
限流后端 LLM 限流是硬约束
3~5 并发即触发限流，xdist 并行度被锁死（默认 3、硬上限 5）。用例越多，全量跑得越久。
噪声假失败有毒
LLM 非确定 + 半截渲染，海量断言 = 海量噪声。红了没人看，用例就废了。
对策（D11 定稿）
定位器多候选回退
testid > role+name > placeholder/label > text > css/xpath，改版只修定位器仓库。
断言只打稳定结构标记
组件 / 状态 / 结构，不碰 LLM 措辞；基础原语必须以 assert 收口。
用例总量控制
v1 只做 20~50 条核心链路，按 P0/P1 分级，冒烟与全量分开跑。
原则：只测外部行为——核心链路先绿、且持续可信，比用例数量更重要。

之后的打算

顺序已排定：先把稳定性和门禁收口，再上生成器，最后才是影响分析与判定。
近期 评审 P1/P2 收口
auth 加固、裸 selector 机械门禁、失败 trace 留存、xdist 并行（≤5，超限拒绝启动）、429 退避重试。
票 04 动作原语库
两档制落地：语义原语（含完成判定/取证）+ 基础原语；基础原语必须以 assert 收口，收集期静态检查。
票 07 AI 生成器（opencode skill）
快照 + 业务描述 → flow 草稿 diff，人工评审入库；失败修复也走 diff 流，AI 只修资产、不改现场。
票 08 快照 diff 影响分析
页面改版后重爬比对，输出受影响的定位器 / 页面 / flow 清单——直接圈定「这次要修哪些用例」。
扩量 核心链路 20~50 条
多轮上下文漂移链路优先；远期接入 LLM-as-Judge（只评结构化维度，措辞评分走旁路不挡门禁）。
里程碑
M0 骨架 ✓ → M1 核心链路覆盖 → M2 AI 生成流水线 → M3 diff / Judge

团队怎么协作：新增一条核心链路

固定五步走，人人（含 AI）走同一条路；评审与验收门是唯一入库通道。
1
探页面
写 configs/crawl/<page>_probe.yaml，探查原语推进状态 + dump_dom，产出页面状态快照。
python -m apw.crawler

2
补定位器
locators/<page>.yaml：候选按优先级书写，来源标 manual / ai，禁止散落裸 selector。
testid > role+name > …
→
3
补页面对象
src/apw/pages/<page>.py：动作 = 语义原语（完成判定 + 失败取证），注册进 default_registry()。
engine/registry.py
→
4
写 flow
flows/<case>.yaml：do / assert / judge，只断言确定性内容；LLM 产出只进 capture_context 证据。
同页面新链路从这步起
→
5
过验收门
收集期 schema 校验 + ruff check + 真实环境绿跑 ≥3 次（防偶发卡死污染结论），绿了才合入。
D15 验收门
硬约束（人人适用）
凭据与内网信息永不入库 失败即取证，禁止自愈 页面元素一律走定位器仓库 引擎不 import pytest / allure 并发 worker ≤ 5（限流） commit：feat/fix + 一句话要点
AI 的权限边界（D10）：只修资产、不改现场——失败后产出修复 diff 人工审合入；探索区临时脚本用完归档 .scratch/ 当生成器素材，升格需人工判定。

交付成果长什么样

代码、用例、报告、生成侧资产与门禁——四块都已落库，可持续演进。
框架本体 src/apw
  • dsl：pydantic schema，收集期校验非法 DSL
  • engine：FlowRunner → StepEvent 事件流
  • pages + locators：语义原语 + 定位器仓库
  • driver：Web / Electron 统一输出 Page
  • reporter：JSON → report.html；pytest 插件 + crawler + sanitize
业务用例 flows/
  • 12 条链路入库：会话冒烟、示例、对话并行切换、Skills 广场、套组广场、报告样式库、操练场
  • 工作流 4 条：手写保存运行 / AI 生成运行
  • 并发 2 个 AI 生成任务 / 并发 2 个 AI 运行任务
  • 并发 UI 逐标签身份核对，串台/卡死判 fail
  • 真实环境 3 次绿跑，冒烟持续绿灯
运行产物 reports/
  • flow 级 JSON：输入/输出/断言明细/耗时/截图
  • run 汇总：三态 passed/failed/skipped + 跳过原因
  • report.html：单文件零依赖，会话结束自动渲染
  • capture_context：用户输入/推理/思考/最终答案
  • 失败含取证包：归因 + 复现 + 信号时间线 + 冻结截图
生成侧资产与门禁 crawler + tests
  • 状态化爬虫 + page: probe 探查原语
  • 快照骨架：状态路径标注 + 定位器候选
  • 落盘自动脱敏：映射表 + 通用模式兜底
  • tests 全绿；tests/test_no_secrets.py 红线门禁
  • 文档：docs/SPEC.md（24 条决策记录）+ AGENTS.md
最小可交付形态：新增一条核心链路 ≈ 写/审一个 YAML 文件——这就是 README 里承诺的生产闭环。
